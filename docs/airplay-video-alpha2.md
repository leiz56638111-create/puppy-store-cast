# 视频直投诊断更新 0.3.0-video-alpha2

与 alpha1 相同独立包名 `cn.local.livingroomcast.airplayvideo`，versionCode2，同签名覆盖 alpha1，不覆盖公开主版 0.1.8。使用入口、Android7 ARM 要求、前台接收方式及能力限制沿用 [alpha1 说明](airplay-video-alpha1.md)。

## 本轮修正

alpha1 在普通媒体会话建立时直接显示“收到屏幕镜像请求”，这个提示缺乏依据。底层 SETUP 只要建立音频／镜像所共用的媒体连接就会触发该回调，尚未知道实际视频流类型。alpha2 改为“已建立媒体连接，等待 App 发送视频”；只有收到镜像编解码配置时才记录镜像视频证据。

新增“连接详情”计数：媒体连接、到达本机视频播放处理器的请求、解析拒绝、设备能力查询、反向通道、播放列表响应、未处理的协议请求；另显示音频格式 ct、usingScreen 与 isMedia 标记。原有“播放请求”表示已送入播放器的有效请求，并非所有到达网络端口的请求。诊断只接纳固定事件／格式标记，不显示视频 URL、Cookie、令牌或会话标识，不写持久日志。

这是提示和诊断更新，未增加 ALAC／纯音频、DRM、私有视频协议或镜像解码，不代表反馈 App 已能播放。

## 这次反馈能证明什么

用户截图显示 App 内 AirPlay 设备列表能看到并选中接收器；电视为 Sony BRAVIA BF1 / Android12 / API31，安装 alpha1，已建立媒体会话但未有送入播放器的有效请求（画面 0×0／首帧未显示）。不能据旧“镜像请求”文案判定用户选错入口，也不能据“0 次”排除视频请求到达后解析失败。App 名称、具体视频及选择设备后是否回播放器继续播放暂未知。

可能包括仅选择了音频路由／尚未实际开始播放、App 不支持视频外播、握手或视频请求与本机接收协议不兼容。仅凭截图不能确认任一根因，也无证据判断为电视解码器或 DRM 导致。

## 如何复测

1. 覆盖安装 alpha2，退出其他接收软件，打开此测试包。
2. 先在 iPhone 上正常播放同一视频，再从 App 内 AirPlay 选择“小狗便利店投屏·直投测试”；回到播放器确认继续播放，等 10–15 秒。
3. 打开电视“连接详情”，反馈新增的计数、音频标记、状态，以及 App 名／版本、iPhone 型号／系统和手机画面状态。
4. 再使用相册中的单个本地短视频或 Safari 普通视频对照。Apple 文档也明确部分 App 不支持 AirPlay；这只是缩小范围的对照，并非宣称这些来源已经兼容本测试包。

若相册／Safari 成功而目标 App 失败，优先调查目标 App 路径；若都没有有效视频请求，优先查接收端握手／协议兼容；有请求且显示“解析拒绝”时调查格式；已交播放器而报错时再查地址访问／媒体解码。以上为排查方向，不是确定根因。

Android12 ARM64 模拟器 9 项原生检查通过，直投 3 项与镜像库 52 项单元检查通过，Lint 0 错误／11 警告。新增检查验证普通媒体／音频回调不会直接标记镜像，且原生拒绝的视频请求能进入诊断计数。详见随包验收 JSON；模拟器／合成视频通过不等于真实 iPhone 或 App 播放验收。本次未上传 GitHub。
